# INF-6 — Совместимость с duckdb 2.0 (`.pl()` убран с соединения)

- **Эпик:** E0 — Scaffolding & инфраструктура
- **Статус:** done
- **Зависимости:** DATA-5, AN-1

## Описание

duckdb 2.0.0 убрал метод `.pl()` с `DuckDBPyConnection`, оставив его только на
`DuckDBPyRelation`. Два вызова в коде перестали работать — **в рантайме**, а не
только по типам.

## Контекст

`pyproject.toml` объявляет `duckdb>=1.0` без верхней границы, поэтому CI ставит
свежайшую версию. С выходом 2.0.0 Quality gate стал падать на всех трёх версиях
Python; локально проблема не воспроизводилась, потому что в venv остался duckdb
1.5.4.

Падение **не было вызвано** ни одним PR — `main` был красным начиная с `eb5209f`
(28.10), включая мержи #21 и #22. Это дрейф зависимости, а не регрессия кода.

Проверка на 2.0.0 показала, что отказ рантаймовый, а не типовой:

```
has .pl on con: False
AttributeError: '_duckdb.DuckDBPyConnection' object has no attribute 'pl'
```

mypy просто поймал это первым (шаг Mypy падает до шага Pytest), поэтому в логах CI
видны только ошибки типов — `pytest` до запроса не доходил.

## Решение

- `con.execute(sql).pl()` → `con.sql(sql).pl()` в двух местах:
  `data/storage/duckdb_store.py` (DATA-5) и `analytics/queries.py` (AN-1).
  `con.sql()` возвращает `DuckDBPyRelation`, у которого `.pl()` остался.
- Результат присваивается аннотированной переменной: в стабах duckdb 2.0 `.pl()`
  объявлен как `Any`, а `mypy --strict` запрещает возвращать `Any` из функции,
  объявленной как `-> pl.DataFrame`.
- Верхнюю границу версии **не** ставим: `con.sql().pl()` работает и на 1.x, и на
  2.x, проверено на обеих.

`register()` и `CREATE VIEW` в 2.0 не изменились — остальной код не затронут.

## Критерии приёмки (DoD)

- [x] `ruff`, `mypy --strict`, `pytest` зелёные на duckdb 2.0.0.
- [x] То же зелёное на duckdb 1.5.4 (нижняя граница диапазона не сломана).
- [x] Исправлены оба вызова; других обращений к удалённому API в `src/` нет
      (проверено `grep`).

## Что осталось открытым

Корневая причина — **незафиксированные зависимости в CI**. Любой следующий мажор
любой зависимости снова покрасит `main`, причём незаметно для разработчика с старым
venv. Варианты: lock-файл или `constraints.txt` для CI, либо верхние границы в
`pyproject`. Решение требует отдельного обсуждения и в этот тикет не входит.
