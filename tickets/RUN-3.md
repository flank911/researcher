# RUN-3 — CLI построения режимных фич (`time_slice_features`)

- **Эпик:** E7 — First real research run
- **Статус:** done
- **Зависимости:** REG-2, RUN-2

## Описание

Команда `build-features`: `build_time_slice_features` (REG-2) → персистентная
таблица `time_slice_features` в Parquet, пригодная как вход для REG-3 (RUN-5).

## Контекст

REG-2 реализовал `compute_slice_features` / `build_time_slice_features` и схему
`TIME_SLICE_FEATURE_COLUMNS`, но вызвать их можно только из Python, и результат
никуда не сохраняется. Для реального прогона нужна таблица на диске: фичи считаются
один раз по истории и затем многократно джойнятся с результатами экспериментов.

## Решение

```
trading-research build-features --config configs/experiments/<...>.yaml \
  [--data-root data/raw] [--features-root data/features]
```

Слайсы и диапазон берутся из того же конфига эксперимента, что и прогон, — иначе
`time_slice_id` в фичах и в таблице AN-1 разойдутся и join в RUN-5 даст пустоту.

Выход: `{features_root}/{experiment}/time_slice_features.parquet`.

## Критерии приёмки (DoD)

- [x] Таблица строится по конфигу и сохраняется в Parquet со схемой REG-2.
- [x] `time_slice_id` совпадает с теми, что генерирует `run-experiment` на том же
      конфиге (тест на согласованность ключей join).
- [x] Отсутствие funding/OI/LS не ломает построение — соответствующие колонки
      остаются `null` (как и задумано в `SliceFeatures`).
- [x] Повторный запуск перезаписывает таблицу идемпотентно.

## Как сделано

`cli/build_features.py` + команда `build-features`. Выход —
`{features_root}/{experiment}/time_slice_features.parquet`, перезаписывается целиком.

**Слайсы берутся не просто из того же конфига, а той же функцией.**
`generate_slices_for` переиспользуется из `cli/run_experiment.py` (её вынесли в
RUN-1 именно под это). Копия кода здесь была бы хуже всего: при расхождении
`time_slice_id` join в RUN-5 схлопнулся бы **молча** — left-join просто вернул бы
`null` во всех режимных колонках, без единой ошибки. Поэтому в DoD отдельный пункт,
а в тестах — не только сравнение множеств `time_slice_id`, но и фактический
`attach_regime_features` поверх реальных выходов обеих команд с проверкой, что
режимные колонки заполнены.

**Отсутствующий ряд нормализуется в `None`, а не в пустой DataFrame.**
`ParquetStore.read_series` на незаполненном датасете отдаёт фрейм **без колонок**, а
REG-2 фильтрует ряд по `open_time` — то есть передача такого фрейма падала бы с
`ColumnNotFoundError`. Контракт `SliceFeatures` ожидает именно `None` как «данных
нет». Предпосылка зафиксирована в тесте (`read_series` действительно отдаёт фрейм без
колонок), чтобы фикс не стал загадкой, если поведение store однажды изменится.

**`TIME_SLICE_FEATURE_SCHEMA` вынесена в публичный API REG-2.** Раньше схема жила в
приватной `_table_schema()`, и построить пустую таблицу с правильными типами извне
было нельзя. Нужна в двух местах: здесь (нет свечей ни по одному символу) и в RUN-5
(пустой join). `_table_schema()` оставлена как обёртка — её поведение не изменилось.

Побочно: строка `cli/` в README приведена к фактическому списку модулей. Оттуда ушёл
`build_dataset`, который был заявлен, но никогда не существовал. Строка `analytics/`
с несуществующим `reports` намеренно не тронута — там открытый вопрос, нужен ли
модуль вообще (решается в RUN-6 / RUN-7).
