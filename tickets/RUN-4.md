# RUN-4 — CLI walk-forward и holdout + секции конфига

- **Эпик:** E7 — First real research run
- **Статус:** done
- **Зависимости:** WF-2, WF-3, EXP-6

## Описание

Весь эпик E5 доступен только из Python. Добавить команду `walk-forward` и секции
`walk_forward` / `holdout` в `ExperimentConfig`, чтобы финальная проверка стратегии
(принцип №8 из README — «финальная проверка только walk-forward») была исполнима из
CLI.

## Контекст

`run_walk_forward` (WF-2), `generate_walk_forward_folds` (WF-1) и весь модуль
`holdout.py` (WF-3) не упоминаются ни в `cli/`, ни в `config.py`.
[ExperimentConfig](../src/trading_research/config.py) содержит `data`,
`time_slices`, `strategy`, `params_grid`, `execution`, `slice_mode`, `metrics`,
`output` — ни одного поля про фолды или holdout.

То есть сейчас платформа умеет только то, что README называет переоптимизированным
поиском (сетка по слайсам), а честный out-of-sample из CLI недостижим.

## Решение

Секции конфига:

```yaml
walk_forward:
  train_span: 6          # периодов train
  test_span: 1           # периодов test
  step: 1
  select_by: sharpe       # метрика отбора на train

holdout:
  end: "2026-01-01"       # всё после — untouched, в research не попадает
```

Команда:

```
trading-research walk-forward --config <...> [--data-root] [--results-root]
```

Выход: `selections` по фолдам, склеенная OOS-кривая, OOS-метрики и
`HoldoutReport` (через `save_holdout_report`) в каталоге эксперимента.

`assert_research_only` вызывается **до** прогона: если research-данные залезают в
holdout-окно, команда падает, а не предупреждает.

## Критерии приёмки (DoD)

- [x] Секции `walk_forward` / `holdout` валидируются pydantic с читаемыми ошибками.
- [x] `walk-forward` печатает выбор по фолдам и OOS-метрики, сохраняет OOS-кривую.
- [x] `HoldoutReport` сохраняется в каталог эксперимента.
- [x] Попытка прогнать research на данных, пересекающих holdout, падает
      (`assert_research_only`).
- [x] Отсутствие секции `holdout` допустимо — тогда holdout-шаг пропускается.

## Как сделано

`cli/walk_forward.py` + команда `walk-forward`. Артефакты —
`{results_root}/{experiment}/wf/{symbol}/`: `oos_equity.parquet`,
`wf_selections.json`, `holdout_report.json`.

**Окна заданы в днях, а не «в периодах».** Отклонение от исходного плана тикета
(`train_span: 6`). Причина конкретная: `generate_walk_forward_folds` (WF-1) принимает
`timedelta`, а календарный месяц в `timedelta` точно не выражается. Поле «6 периодов»
потребовало бы молча считать месяц за 30 дней — то есть вернуть в конфиг скрытое
допущение. В днях допущение выбирает автор конфига, и оно видно в имени поля.

**`holdout.start`, а не `end`.** В плане тикета стояло `holdout: end:` с комментарием
«всё после — untouched», что противоречит само себе: это начало резерва, а не его
конец. Имя приведено к семантике `HoldoutSplit.holdout_start`.

**Порядок шагов выражает политику WF-3, а не удобство:**

1. Резерв отрезается первым (`research_data`), сразу после чего результат проверяется
   `assert_research_only`. Проверка избыточна по построению — и именно поэтому
   полезна: она ловит ошибку в самом разрезании, а не доверяет ему.
2. Фолды строятся до начала holdout, а не до конца данных, иначе test-окно последнего
   фолда залезло бы в резерв. На реальном конфиге это 48 фолдов, ни один не
   пересекает границу.
3. Holdout считается один раз, в конце, на параметрах **последнего** фолда — это то,
   что реально «пошло бы в бой». Альтернатива (самые частые параметры по фолдам)
   устойчивее, но отвечает на другой вопрос: «что работало в среднем», тогда как
   holdout проверяет именно вывод исследования.

**Деградация считается от OOS-оценки, а не от train-скора.** Сравнивать holdout с
train означало бы измерять переоптимизацию дважды: train заведомо оптимистичен.
Вопрос, на который отвечает отчёт, — «был ли оптимистичен даже честный OOS-прогноз».

**`select_by` валидируется на уровне конфига**, а не в середине прогона: опечатка
вроде `sharp` падает при загрузке YAML. Важный нюанс pydantic — валидатор не
исполняется для значения по умолчанию, поэтому успешная ветка покрыта отдельным
тестом с явной метрикой (без него она не вызывалась вовсе — нашлось по покрытию).

Главный инвариант под тестом — в OOS-кривую попадают **только** бары test-окон:
протечка train завысила бы OOS-метрики, причём молча.
