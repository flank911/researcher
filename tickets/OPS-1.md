# OPS-1 — Ежедневный инкрементальный сбор OI/LS: история, которую нельзя догрузить

- **Эпик:** E8 — Эксплуатация данных
- **Статус:** done
- **Зависимости:** REG-5, REG-4
- **Критический путь:** да (окно необратимо)

## Описание

Binance отдаёт open interest и long/short ratio только за последние ~30 дней
(см. [REG-4](REG-4.md)). Это значит: история этих рядов **создаётся только
собственным сбором**. Каждый день без сбора — день, который в датасет уже не
попадёт никогда.

Остальные ряды такого свойства не имеют: свечи и funding доступны за всю историю и
догружаются в любой момент.

## Контекст

Состояние store на 2026-10-30:

| Ряд | Покрытие | Догружаемо? |
|-----|----------|-------------|
| candles | 2022-01-01 … 2026-09-30, 156 060 бар | да, в любой момент |
| funding | 2022-01-01 … 2026-09-30, 31 362 строки | да, в любой момент |
| open_interest | 2026-10-02 … 2026-10-30 (4h), 2026-10-09 … (1h) | **нет, только вперёд** |
| long_short_ratio | то же | **нет, только вперёд** |

Прогон [RUN-7](RUN-7.md) показал последствия: `oi_change_pct` и `ls_ratio_avg` —
114 NULL из 114 строк `time_slice_features`, то есть две из девяти фич режима не
проверены ни на одном реальном числе. Эпик E6 в этой части существует только как код.

Окно OI/LS сейчас заканчивается на `2026-10-30` — то есть разрыв ещё нулевой.
Любая задержка его открывает, и закрыть его будет нечем.

## Решение

- Команда инкрементального сбора: читает последний сохранённый таймстамп из
  store по каждой паре символ × таймфрейм, запрашивает `[последний + период, now)`,
  пишет через идемпотентный `_upsert` (он уже есть в `ParquetStore`).
- Набор символов и таймфреймов — из конфига, а не из аргументов: сбор должен
  переживать смену состава без правки расписания.
- Запуск по расписанию (launchd / cron / GitHub Actions — выбрать по месту; данные
  лежат локально, поэтому скорее launchd). Частота — не реже раза в сутки с запасом
  к окну retention; при частоте раз в неделю одна пропущенная итерация уже рвёт
  историю.
- Отчёт о покрытии после каждой итерации: сколько строк дописано, какой разрыв
  остался, какие пары отстали. Молчаливый успех здесь неприемлем — провал
  обнаружится через месяц, когда данные уже потеряны.
- Нельзя делать до [REG-5](REG-5.md): пагинация `/futures/data/*` сейчас теряет
  начало запрошенного окна, то есть регулярный сбор будет накапливать дыры с той
  же регулярностью.

## Критерии приёмки (DoD)

- [x] Команда догружает каждый ряд от последнего сохранённого бара до `now`,
      повторный запуск ничего не дублирует и не теряет.
- [x] Набор пар берётся из конфига.
- [x] Вывод показывает дописанные строки и остаточный разрыв по каждой паре.
- [x] Расписание задокументировано; описано, как проверить, что оно живо.
      Агент **не загружен** — это постоянная настройка в системе пользователя,
      её ставит он сам одной командой из README.
- [x] Пропущенная итерация видна: разрыв в выводе, а не в тишине.
- [x] Тест на подставном транспорте: догрузка от последнего бара, идемпотентность
      повторного запуска, пустой store как частный случай.

## Как сделано

Команда `update-market-data --config <config.yaml> [--series …]`
(`cli/update_market_data.py`). Логика сводится к трём решениям, каждое из которых
следует из необратимости окна retention.

**Начало окна — из store, а не из аргументов.** `_last_stored` читает последнюю
точку ряда, `_resume_from` шагает за неё на период (у funding — на 1 мс, своего
периода у него нет). Шаг нужен не для экономии: upsert дубль бы снял, но число
дописанных точек врало бы на единицу, а именно по нему и смотрят, жив ли сбор.

**Правая граница — предыдущая полная точка**, `floor(now, period)`, а не `now`.
Точка текущего периода может быть ещё не опубликована, и её отсутствие выглядело
бы как неполное покрытие на каждом запуске. Следующая итерация её подберёт.

**Невосполнимый пропуск назван вслух.** `SeriesUpdate.lost` — разрыв между тем,
откуда следовало продолжить, и тем, откуда вообще можно. Это не «ещё не
загружено», а «загрузить больше нельзя», и в выводе это отдельная пометка
`НЕВОСПОЛНИМЫЙ ПРОПУСК`, а не строка в общем ряду.

Актуальный ряд **не** выпадает из отчёта: строка «актуален до …, догружать нечего»
есть на каждую пару. Иначе «ряд актуален» и «ряд выпал из сбора» выглядят
одинаково — тишиной, а отличать их нужно именно по выводу расписания.

### Окно retention замерено, а не взято из документации

Прямая проверка эндпоинтов 2026-10-30 (`openInterestHist` и
`globalLongShortAccountRatio`, BTCUSDT 1h):

| `startTime` | Ответ |
|-------------|-------|
| 25, 28, 29 дней назад | HTTP 200, точки есть |
| 30, 31, 32, 35, 40 дней назад | HTTP 400, `-1130 parameter 'startTime' is invalid` |

Граница — ровно 30 дней, одинаково у обоих рядов. В коде `RETENTION = 30 д`, а
кламп идёт по `SAFE_RETENTION = 29 д`: сутки запаса покрывают расхождение часов и
время самого запроса, иначе сбор у границы окна падал бы случайным образом.

Кламп закрывает первые два пункта DoD тикета [REG-4](REG-4.md) для пути сбора:
`-1130` до пользователя не доходит, историческое начало урезается до доступного с
явной пометкой. За REG-4 остаётся его собственная часть — покрытие фич в
`build-features` и отличие «нет данных» от «нет корреляции» в `analyze-regimes`,
плюс кламп в разовом `fetch-market-data`.

### Расписание

`ops/update-market-data.sh` — одна итерация с логом в `data/logs/`;
`ops/com.trading-research.update-market-data.plist` — launchd-агент с
`StartInterval` 6 часов. Интервал, а не календарное время: на ноутбуке
календарную задачу можно проспать, а интервальную launchd запускает при
пробуждении. Шесть часов при окне в 30 дней — большой запас, то есть терять данные
расписание начнёт только если промолчит месяц.

Проверка «живо ли оно» построена на данных, а не на логе: ручной запуск команды на
работающем сборе отвечает «актуален, догружать нечего», а на умершем — покажет
разрыв за всё пропущенное время. Лог и `launchctl list` остаются для разбора
причины. Подробно — в README.

### Первая реальная итерация

Прогон 2026-10-30 на `ma_cross_multi_1h_4h` (3 символа × 2 таймфрейма):

- догружено 63 точки OI и 54 точки LS до правой границы, 540 точек funding за
  месяц, который накопился с прогона RUN-7;
- повторный запуск: «0 точек по 18 рядам, уже актуальны: 12, пропусков нет» —
  идемпотентность на живых данных.

Отдельно восстановлена дыра, которую оставил сам дефект [REG-5](REG-5.md): 1h-ряды
OI и LS начинались с 2026-10-09 05:00 вместо 2026-10-02, и это было последнее
окно, когда их ещё можно было догрузить — 2026-10-02 находилось в 29 днях от
«сейчас». Теперь по всем шести парам 672 точки с 2026-10-02, покрытие полное.

## Что осталось за рамками

Инкрементальная догрузка **свечей** — [OPS-2](OPS-2.md): этой командой покрыты
только рыночные ряды (funding/OI/LS), и funding в ней уже догружается от последней
точки, то есть OPS-2 сводится к свечам.
