# DATA-8 — CLI-команда валидации датасета

- **Эпик:** E1 — Data Core
- **Статус:** todo
- **Зависимости:** DATA-3, DATA-2
- **Критический путь:** нет

## Описание

DATA-3 (`validate_candles`, `validate_series`, `ValidationReport`, `save_report`)
доступен только из Python. Проверить качество загруженных данных из CLI нечем.

## Контекст

Вскрыто на прогоне [RUN-7](RUN-7.md): тикет прямо требовал «отдельно проверить
качество данных `validators.py` на реальной истории Binance», и для этого пришлось
писать одноразовый скрипт — читать `ParquetStore`, обходить пары символ × таймфрейм,
звать валидатор, печатать отчёт. Это ровно тот класс разрыва, который закрывали
[RUN-1](RUN-1.md)…[RUN-5](RUN-5.md): библиотека есть, в CLI-путь не подключена.

Отчёт при этом уже спроектирован под внешнее использование: `ValidationReport` —
иммутабельная pydantic-модель с `model_dump_json`, и рядом лежит `save_report`,
у которого в CLI нет ни одного вызывающего.

## Решение

- Команда по образцу остальных:

  ```
  trading-research validate-data --config <config.yaml> [--out <dir>] [--strict]
  ```

  Берёт символы, таймфреймы и диапазон из конфига эксперимента (как
  `build-features`), валидирует каждую пару, печатает сводку одной строкой на пару и
  складывает JSON-отчёты через `save_report`.
- `--strict` — ненулевой код возврата при найденных дефектах, чтобы шаг можно было
  поставить в пайплайн перед `run-experiment`.
- Сводка должна показывать то, на что смотрят глазами: бары, пропуски, дубли,
  монотонность, нарушения OHLC, выбросы.
- Ряды funding/OI/LS валидируются `validate_series` той же командой — иначе второй
  валидатор останется без CLI.

## Критерии приёмки (DoD)

- [ ] `validate-data` работает по конфигу и по явным `--symbol/--timeframe`.
- [ ] JSON-отчёты сохраняются; путь виден в выводе.
- [ ] `--strict` даёт ненулевой код возврата при дефектах.
- [ ] `validate_series` вызывается для загруженных рядов, а не только свечи.
- [ ] Тест на CLI-команду (на временном store, без сети).
