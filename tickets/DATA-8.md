# DATA-8 — CLI-команда валидации датасета

- **Эпик:** E1 — Data Core
- **Статус:** done
- **Зависимости:** DATA-3, DATA-2, DATA-7
- **Критический путь:** нет

## Описание

DATA-3 (`validate_candles`, `validate_series`, `ValidationReport`, `save_report`)
доступен только из Python. Проверить качество загруженных данных из CLI нечем.

## Контекст

Вскрыто на прогоне [RUN-7](RUN-7.md): тикет прямо требовал «отдельно проверить
качество данных `validators.py` на реальной истории Binance», и для этого пришлось
писать одноразовый скрипт — читать `ParquetStore`, обходить пары символ × таймфрейм,
звать валидатор, печатать отчёт. Это ровно тот класс разрыва, который закрывали
[RUN-1](RUN-1.md)…[RUN-5](RUN-5.md): библиотека есть, в CLI-путь не подключена.

Отчёт при этом уже спроектирован под внешнее использование: `ValidationReport` —
иммутабельная pydantic-модель с `model_dump_json`, и рядом лежит `save_report`,
у которого в CLI нет ни одного вызывающего.

## Решение

- Команда по образцу остальных:

  ```
  trading-research validate-data --config <config.yaml> [--out <dir>] [--strict]
  ```

  Берёт символы, таймфреймы и диапазон из конфига эксперимента (как
  `build-features`), валидирует каждую пару, печатает сводку одной строкой на пару и
  складывает JSON-отчёты через `save_report`.
- `--strict` — ненулевой код возврата при найденных дефектах, чтобы шаг можно было
  поставить в пайплайн перед `run-experiment`.
- Сводка должна показывать то, на что смотрят глазами: бары, пропуски, дубли,
  монотонность, нарушения OHLC, выбросы.
- Ряды funding/OI/LS валидируются `validate_series` той же командой — иначе второй
  валидатор останется без CLI.

## Критерии приёмки (DoD)

- [x] `validate-data` работает по конфигу и по явным `--symbol/--timeframe`.
- [x] JSON-отчёты сохраняются; путь виден в выводе.
- [x] `--strict` даёт ненулевой код возврата при дефектах.
- [x] `validate_series` вызывается для загруженных рядов, а не только свечи.
- [x] Тест на CLI-команду (на временном store, без сети).

## Как сделано

`cli/validate_data.py` + команда `validate-data`. Символы, таймфреймы и диапазон
берутся из конфига; `--symbol` / `--timeframe` сужают набор пар, диапазон всегда
конфигов — проверять надо ровно то окно, на котором пойдёт прогон. На каждую пару
печатается заголовок и по строке на датасет (свечи + funding/OI/LS), JSON-отчёт
каждого датасета сохраняется через `save_report`, путь стоит в той же строке.

Два места, где прямолинейная реализация соврала бы:

- **Шаг ряда ≠ таймфрейм партиции.** У funding расписание выплат задаёт биржа
  (сейчас 8 ч), а `timeframe` в пути хранения — только ключ партиции. Проверка с
  шагом `1h` отчиталась бы о пропуске на каждой второй точке, поэтому шаг funding
  выводится из данных (`infer_step`, допуск 1 %). Не опознался — проверка
  пропусков честно пропускается, а не делается по выдуманному шагу.
- **Окно сверки для OI/LS урезано retention'ом.** Ожидаемое начало считается тем
  же `clamp_to_retention`, что и при загрузке (REG-4): более старой истории у
  биржи не существует, и считать её пропуском нечестно. Если диапазон конфига
  целиком старше окна — это сказано в строке вывода, а границы не сверяются.

Отсутствие funding/OI/LS — не дефект (они опциональны по контракту
`build_features`, пустую фичу ловит REG-4 на своём шаге); отсутствие свечей —
дефект. Без `--strict` команда остаётся диагностикой: дефекты видны, код 0.

Попутно закрыт скрытый краш валидатора: времена выплат Binance плавают на единицы
миллисекунд (8 ч + 1 мс встречается в истории сотнями), расстояние «чуть больше
шага» давало `missing_bars=0` при `Field(gt=0)` — то есть первая же валидация
funding на реальных данных упала бы с `ValidationError`. Пропуск теперь считается
по числу невышедших точек, а не по расстоянию.

На реальной истории команда сразу нашла расхождение, которого никто не видел:
конфиг `ma_cross_btc_1h_monthly` просит данные с 2021-01-01, а в store история с
2022-01-01 — год пропуска, `--strict` даёт код 1.
