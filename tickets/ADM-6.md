# ADM-6 — Контроль: запуск шагов пайплайна из админки

- **Эпик:** E10 — Админка
- **Статус:** todo
- **Зависимости:** ADM-3, EXP-6, DATA-8, OPS-1, OPS-2
- **Критический путь:** нет (наглядность работает и без контроля)

## Описание

Кнопки, запускающие шаги пайплайна (`update-data`, `update-market-data`,
`validate-data`, `build-features`, `run-experiment`, `walk-forward`), с логом,
кодом возврата и историей запусков.

## Контекст: главный риск — второй вход в пайплайн

Проект пять раз ловил расхождение «библиотека есть, CLI-пути нет»
([RUN-1](RUN-1.md)…[RUN-5](RUN-5.md), [DATA-8](DATA-8.md)) и шестой раз нашёл его
в `random_search` ([RES-2](RES-2.md)). Админка, повторяющая логику шагов, заводит
то же расхождение в обратную сторону: «в панели посчиталось, из CLI не
повторяется». Для платформы, у которой воспроизводимость — принцип №5, это худшее
из возможных последствий удобства.

Поэтому вопрос не «как сделать кнопки», а «как сделать так, чтобы кнопка не стала
вторым путём исполнения». Два варианта:

| Вариант | За | Против |
|---|---|---|
| Звать те же функции в процессе сервера (`run_experiment_from_config` и т. п.) | Доступен прогресс и структурированный результат | Второй контекст исполнения: свои воркеры, своё окружение, свои коды возврата; расхождение с CLI не видно, пока не разойдётся |
| **Подпроцесс `trading-research <команда>`** | Ровно один путь исполнения, тот же код возврата, тот же вывод, что видит человек в терминале | Прогресс только построчно из stdout, тесты сложнее |

Выбран подпроцесс: совпадение с CLI здесь важнее гранулярного прогресса. Админка
становится не вторым входом, а пультом к существующему.

## Решение

- `admin/jobs.py`: очередь задач, по одной на эксперимент/конфиг одновременно.
  Задача — это `(команда, аргументы)`, запускаемая как подпроцесс
  `sys.executable -m trading_research.cli.main …`.
- Запись о задаче: `data/logs/jobs/<id>.json` (команда, аргументы, время,
  код возврата, статус) и `<id>.log` — полный вывод.
- Опасность называется до запуска: `run-experiment` и `walk-forward` пишут в
  результаты, `fetch-*`/`update-*` ходят в сеть и тратят лимит биржи. Подтверждение
  перечисляет, что изменится и куда.
- Отмена останавливает процесс и помечает задачу прерванной.
- Флаг `--read-only` у `trading-research admin` отключает контроль целиком: режим
  наблюдения остаётся доступным, если панель открыта «на посмотреть».
- Сервер по-прежнему слушает только `127.0.0.1`.

## Критерии приёмки (DoD)

- [ ] Каждая кнопка соответствует существующей команде CLI один к одному; список
      соответствий есть в тикете и в докстринге модуля.
- [ ] Модуль контроля не импортирует движок, оркестратор и загрузчики данных —
      проверяется тестом на импорты (это и есть гарантия «не второй путь»).
- [ ] Две одновременные задачи на один эксперимент невозможны (тест).
- [ ] Код возврата и полный лог видны в UI и сохранены на диск; у прерванной
      задачи статус «прервана», а не «успешно».
- [ ] `--read-only` убирает все обработчики запуска (тест по таблице маршрутов).
- [ ] Запуск опасного шага без подтверждения невозможен (тест).
- [ ] Прогон одного шага через админку и тот же шаг из терминала дают одинаковый
      результат — сверка `run_hash` на `run-experiment`.
