# RUN-1 — Подключить resume/dedupe и параллелизм к CLI-прогону

- **Эпик:** E7 — First real research run
- **Статус:** done
- **Зависимости:** EXP-3, EXP-4, EXP-5, EXP-6
- **Критический путь:** да

## Описание

`RunCache` (EXP-3), `run_parallel` (EXP-5) и `ResultsStore` (EXP-4) существуют,
покрыты тестами, но **не подключены ни к одному продакшн-пути**. Подключить их к
`cli/run_experiment.py`, чтобы реальный прогон был возобновляемым и многопроцессным.

## Контекст

`grep` по `src/` показывает: вне собственных модулей `experiments/cache.py`,
`experiments/parallel.py` и `experiments/results_store.py` не импортируются нигде,
кроме единственной ссылки `queries.performance_from_store`.

Фактический путь команды `run-experiment`
(`run_experiment_from_config`, [cli/run_experiment.py](../src/trading_research/cli/run_experiment.py)):

```
config → DuckDBStore.read_window → expand_grid
       → orchestrator.run_experiment   (последовательно, без кэша)
       → build_parameter_performance   (из records в памяти)
       → save_performance_table        (performance.parquet напрямую)
```

То есть реальный многочасовой прогон сегодня:

- **однопроцессный** — `parallel.py` не задействован, хотя EXP-5 закрыт;
- **без resume** — падение на середине сетки теряет весь прогон, `run_hash` не
  считается, dedupe не работает;
- **в обход каталога** — `ResultsStore` не наполняется, артефакты ранов (trades,
  equity curve) не сохраняются, хотя `output.save_trades` и
  `output.save_equity_curve` в конфиге стоят в `true` и сейчас ни на что не влияют.

Последнее особенно важно: три закрытых тикета (EXP-3/4/5) дают нулевой эффект на
реальном прогоне, и обнаруживается это только при попытке его сделать.

## Решение

- `run_experiment_from_config` считает `run_hash` на комбинацию и спрашивает
  `RunCache` перед прогоном (resume + dedupe).
- Исполнение сетки — через `run_parallel` с опцией `--workers` (дефолт:
  `os.cpu_count()`, `1` — последовательно, для отладки).
- Результаты пишутся в `ResultsStore`, таблица AN-1 строится через
  `performance_from_store`; `output.save_trades` / `save_equity_curve` начинают
  реально управлять сохранением артефактов.
- Флаг `--resume/--no-resume` в CLI, прогресс в stderr (количество
  выполнено/из кэша/осталось).

## Критерии приёмки (DoD)

- [x] `run-experiment` переиспользует результаты из кэша при повторном запуске
      (тест: два прогона, второй не вызывает движок).
- [x] Прерванный прогон доходит до конца при повторном запуске с `--resume`.
- [x] `--workers N` даёт тот же результат, что `--workers 1` (детерминизм
      не зависит от числа процессов).
- [x] `ResultsStore` наполняется, `output.save_trades`/`save_equity_curve`
      управляют артефактами.
- [x] Таблица AN-1 строится через `performance_from_store` и совпадает с прежней
      по содержимому (прежние тесты EXP-6 проходят без изменений).

## Как сделано

**Единица параллельной работы — комбинация параметров, а не отдельный ран.**
Это главное отклонение от исходного плана тикета, и вот почему.

`RunSpec` (EXP-3) описывает ран как `(параметры × слайс)`, а `execute_runs_parallel`
(EXP-5) считает один `RunSpec` независимой единицей. Для дефолтного режима
`CONTINUOUS` (EXP-2) это неверно: там делается **один** прогон на комбинацию по всей
истории, а `segment_by_slice` берёт базой окна equity на баре перед его началом —
то есть слайсы одной комбинации не независимы. Посчитать один `(параметры × слайс)`
изолированно нельзя, не прогнав историю заново, а это `combos × slices` полных
прогонов вместо `combos` — ровно та потеря в `len(slices)` раз, которую EXP-2 и
устраняет.

Поэтому в EXP-5 добавлен `execute_run_groups_parallel`: единица работы — *группа*
ранов (все слайсы одной комбинации). Прежний `execute_runs_parallel` не тронут.
Для `INDEPENDENT` группа тоже остаётся комбинацией — меньше задач, меньше
накладных расходов на пул.

Следствия, которые стоит знать:

- **Dedupe и resume работают на уровне группы.** Частично готовая группа считается
  заново: в `CONTINUOUS` отдельный слайс и нельзя досчитать, а повторная запись
  идемпотентна (`ResultsStore.save_run`). Зафиксировано тестом.
- `max_workers=1` исполняет группы в текущем процессе, без пула — семантика та же,
  что и с пулом (тоже под тестом).
- `dataset_hash` считается контентно по фактически загруженным свечам (DATA-4), а
  `git_commit` — из INF-3. Значит смена данных **или кода** инвалидирует кэш; при
  разработке это означает полный пересчёт после каждого коммита, и это намеренное
  поведение EXP-3, а не недосмотр.
- Воркер получает имя стратегии и пути, а не объект стратегии и DataFrame: данные
  он читает из Parquet-store сам, поэтому в дочерний процесс не уезжает история.
- `--no-resume` удаляет маркеры ранов эксперимента и считает всё заново.
- Выключенный флаг артефакта обнуляет файл, но сохраняет схему (`clear()`), так что
  пустой артефакт остаётся читаемым — как и `trades_to_df([])`.
