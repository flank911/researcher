# ADM-4 — Эксперименты и прогоны: откуда взялось число

- **Эпик:** E10 — Админка
- **Статус:** done
- **Зависимости:** ADM-3, EXP-4, AN-1, AN-2, AN-3, AN-4
- **Критический путь:** да (без этого админка показывает только данные)

## Описание

Страницы эксперимента: состав прогонов, рейтинг и карты параметров, и — главное
— путь от любого числа к прогонам, из которых оно посчитано.

## Контекст

В `catalog.sqlite` эксперимента `ma_cross_multi` лежит 684 прогона: 19 слайсов ×
6 пар × 6 наборов параметров, все `completed`, все с одним `git_commit`
(`e847b0e`) и `dataset_hash` в каждой строке. Чтобы посмотреть, из чего состоит
одна строка рейтинга, сейчас нужно: `analyze-results`, затем `export-results`,
затем SQL к `catalog.sqlite` и чтение parquet по `run_hash`.

Два следствия, которые эта страница обязана снять:

**Происхождение числа нигде не показано.** Принцип №5 — каждый run
воспроизводим, и для этого всё записано: `run_hash`, `dataset_hash`,
`git_commit`. Но ни одна команда их не печатает, так что воспроизводимость
существует в хранилище и отсутствует в выводе.

**Ненадёжные прогоны неотличимы от остальных.** 312 из 684 строк `run_metrics`
имеют `reliable=0` (меньше `min_trades=10` сделок). `walk-forward` такие
результаты помечает ([RUN-9](RUN-9.md)), а `rank_params` ([AN-2](AN-2.md))
усредняет метрику по группе без фильтра и без упоминания флага. Админка **не
должна это чинить** — вопрос «фильтровать ли рейтинг по надёжности» относится к
AN-2 и решается отдельно. Её дело — показать долю и пометить строки, чтобы
решение принималось зная, а не вслепую.

## Решение

Три уровня, каждый — ссылка на следующий:

1. **Список экспериментов:** конфиг, стратегия, число прогонов по статусам,
   покрытие слайсов и пар, доля `reliable=0`, время последнего прогона,
   `git_commit`.
2. **Эксперимент:** рейтинг ([AN-2](AN-2.md)), стабильность
   ([AN-3](AN-3.md)), heatmap ([AN-4](AN-4.md), рисуется существующим
   `plots.py`), фильтры по символу, таймфрейму и метрике. У каждой строки —
   сколько прогонов в неё усреднено и сколько из них ненадёжны.
3. **Прогон:** параметры, метрики, сделки, equity, происхождение (`run_hash`,
   `dataset_hash`, `git_commit`, слайс) и готовая команда, которой он
   воспроизводится — чтобы скопировать, а не собирать по памяти.

## Критерии приёмки (DoD)

- [x] С любой агрегированной метрики есть путь к списку прогонов, из которых она
      посчитана: числа без происхождения на страницах нет.
- [x] Строки с `reliable=0` помечены, доля показана на уровне эксперимента и не
      теряется при фильтрах.
- [x] Страница прогона печатает команду воспроизведения; команда проверена
      запуском (даёт тот же `run_hash`).
- [x] Heatmap и рейтинг считаются существующими `analytics.*`, второй реализации
      нет (проверяется тестом на импорты).
- [x] Эксперимент без прогонов и прогон со статусом `failed` отображаются
      (ошибка видна), а не роняют страницу.
- [x] Время ответа на 684 прогонах замерено; если страница рейтинга собирается
      дольше секунды — указано, что кэшируется и как инвалидируется.

## Как сделано

### Что получилось

Четыре уровня, каждый — ссылка на следующий: список экспериментов →
эксперимент (рейтинг, карта параметров, устойчивость) → прогоны под выбранным
числом → один прогон с происхождением, метриками, кривой капитала и сделками.
Фильтры по символу, таймфрейму, метрике и осям карты живут в query-строке,
поэтому любой экран — это ссылка, которую можно послать.

### Что показал store, когда путь появился

Эти четыре находки и есть ответ на вопрос тикета «откуда взялось число».

**Рейтинг возглавляет комбинация с худшей надёжностью.** Top-1 по `sharpe` —
`fast_ma=50, slow_ma=200` со средним 0,47. Это среднее по 114 прогонам, и **61 из
них** имеет `reliable=0` — больше половины. На четвёртом месте комбинация, у
которой ненадёжных 36 из 114. То есть порядок строк частично определяется тем,
какая комбинация набрала больше прогонов по две-три сделки.

| Ранг | Параметры | sharpe | Прогонов | Ненадёжных |
|---|---|---|---|---|
| 1 | fast_ma=50, slow_ma=200 | 0,471 | 114 | **61 (54 %)** |
| 2 | fast_ma=10, slow_ma=200 | 0,436 | 114 | 52 (46 %) |
| 3 | fast_ma=20, slow_ma=200 | 0,393 | 114 | **58 (51 %)** |
| 4 | fast_ma=10, slow_ma=100 | 0,192 | 114 | 36 (32 %) |

**Отдельное число выглядит отлично и не значит ничего.** Первый же прогон
эксперимента: `sharpe` 2,35, доходность 18 %, просадка 7 % — **на двух сделках**.
До этой страницы в нём не было видно ничего, что сказало бы «смотреть нельзя».

**Вектор устойчивости AN-3 молча смешивал пары.** `top_quantile_freq` сравнивает
комбинации **внутри слайса**, и докстринг `stability_vector` прямо требует
сначала отфильтровать таблицу до одной пары. Требование не проверялось ничем: на
шести парах в один слайс попадают шесть разных рынков, а колонка `n_slices`
показывает 114 и читается как «114 слайсов», хотя слайсов 19. В read-model поле
названо `table_rows`, а страница говорит о смешении вслух.

**Эксперимент в store сегодня невоспроизводим — по двум причинам сразу.**
`git_commit` всех 684 прогонов — `e847b0e`, а HEAD давно другой. И, что важнее,
`dataset_hash` окна `2022-01-01…2026-10-01` для BTCUSDT 1h сегодня
`fb8fc651bbbf0c5b`, а в прогонах записан `98c9d6f506e2d4f5`: **данные под числами
изменились**, хотя границы окна в конфиге те же. Сырьё обещано неизменным — это
повод разбираться, и теперь он виден нажатием.

Админка ничего из этого **не чинит**. Фильтровать ли рейтинг по надёжности —
вопрос к AN-2; решение «усреднять ли ненадёжные» слишком важное, чтобы протащить
его мимо тикета. Дело страницы — показать, чтобы решали зная.

### Пять решений

**Считают существующие `analytics.*`.** Рейтинг — `rank_params` (AN-2),
устойчивость — `stability_vector`/`rank_by_stability` (AN-3), матрица карты —
`build_heatmap` (AN-4), таблица — `load_performance_table` по пути
`experiment_results_path`, то есть ровно то, что читает `analyze-results`. Своих
формул метрик в админке нет ни одной.

**Доля ненадёжных считается рядом с рейтингом, а не внутри него.** `rank_params`
отдаёт `n` — сколько строк усреднено, но не отдаёт, сколько из них ненадёжны, и
дописывать это в AN-2 нельзя: её вывод уже экспортируется (`export-results`).
Счёт берётся из той же таблицы, из которой считался рейтинг, и приклеивается к
строке по `param_hash`.

**Происхождение проверяется, а не печатается.** `RunSpec`, собранный из того, что
показано на странице, обязан дать тот же `run_hash`. Сходится — значит набор
входов полный; не сходится — конфиг разошёлся с прогоном, и это главное, что
нужно сказать о числе раньше любых метрик. На сегодняшнем store сходится 684 из
684.

**Карта параметров — разметка, а не PNG.** В PNG ячейка это тупик, а весь смысл
тикета — чтобы путь к числу продолжался: здесь ячейка ведёт к своим прогонам.
Матрицу по-прежнему считает `build_heatmap`, а `plot-heatmap` остаётся для
отчётов, где картинка и нужна картинкой.

**Проверка данных — по требованию.** Пересчёт `dataset_hash` читает всё окно
свечей (41 617 строк, 0,37 с). Делать это на каждый показ страницы значило бы
удесятерить её время ради вопроса, который задают редко; ссылка «проверить, те ли
сегодня данные» решает это честнее кэша.

### Отступления от плана тикета

| План | Сделано | Почему |
|---|---|---|
| Heatmap рисует `plots.py` (PNG) | Матрица из `build_heatmap`, рисует разметка | Ячейка PNG не может быть ссылкой, а путь от числа к прогонам — суть тикета |
| Сделки и equity как есть | Сделки — первые 200, equity прорежен до 240 точек | Прогон интересен формой кривой и метриками; 2 160 точек в разметке — десятки лишних килобайт |
| — | Проверка `dataset_hash` по требованию | План не предполагал, что данные под прогоном могли измениться; оказалось — изменились |

### Замер на 684 прогонах

Кэша нет нигде: самая тяжёлая страница собирается за 21 мс.

| Страница | Время | Размер |
|---|---|---|
| Список экспериментов | 9 мс | 6,7 КиБ |
| Эксперимент (рейтинг + карта + устойчивость) | 15 мс | 16,8 КиБ |
| Прогоны за одной строкой рейтинга (114) | 17 мс | 61,9 КиБ |
| Все 684 прогона | 21 мс | 342,4 КиБ |
| Один прогон | 24 мс | 20,3 КиБ |
| Он же с проверкой данных | 311 мс | 20,8 КиБ |

Чтения, из которых это складывается: таблица AN-1 — 48 мс на первый разбор,
`rank_params` — 17 мс, `stability_vector` — 23 мс, `build_heatmap` — 7 мс,
`all_runs()` на 684 прогонах — 6 мс.

### Команда воспроизведения: проверена запуском

Тест `test_printed_command_really_reproduces_the_run` прогоняет эксперимент,
берёт со страницы напечатанную строку, запускает **настоящий CLI** подпроцессом в
чистый `--results-root` и проверяет, что `run_hash` получился тот же. Проверка
неслучайна: подмена `--data-root` в команде её роняет.

На реальном store та же команда сегодня даст **другой** `run_hash` — и страница
говорит об этом обеими причинами: `git checkout e847b0e…` в самой команде и
красная строка про изменившиеся свечи после проверки данных.

### Тесты и мутации

50 новых тестов: 33 в `tests/test_admin_runs.py`, 15 добавлено в
`tests/test_admin_web.py` и 2 — из запрета своего доступа к данным, который в
`tests/test_admin_state.py` распространён на весь пакет. Всего в проекте 709.

Тесты нашли дефект до коммита: шаг прореживания кривой считался делением вниз,
поэтому лимит в 240 точек давал 300.

Тесты проверены 25 мутациями — все убиты:

| Мутация | Чем убита |
|---|---|
| Ненадёжные считаются не по набору параметров | Строка рейтинга разошлась с прогонами за ней |
| «Больше половины» становится «хоть один» | Помечены оказались все строки |
| Доля по эксперименту считается после фильтра | Доля исчезла при фильтре по паре |
| Фильтр по подмножеству параметров игнорируется | Ячейка карты привела не к своим прогонам |
| «Только надёжные» захватывает прогоны без метрик | Упавший прогон попал в надёжные |
| Идентичность объявляется сошедшейся без пересчёта | Изменённый конфиг перестал ловиться |
| В идентичность не входит модель исполнения | Пересчёт разошёлся с `run_hash` |
| Команда не возвращает к коммиту прогона | Нет `git checkout` на другом HEAD |
| Кривая не прореживается | Точек больше лимита |
| Плоская кривая делится на ноль | `shape()` упал |
| Ячейка карты всегда самая яркая | Нормировка 0..1 сломалась |
| Смешение пар в AN-3 не замечается | Исчезло предупреждение и флаг |
| Сделки не ограничиваются числом | Показаны все вместо первых N |
| Проверка данных сравнивает не то окно | Совпадение хэшей пропало |
| Мусор в query доходит до аналитики | Пятисотка вместо страницы |
| Идентичность пересчитывается по чужому конфигу | «Сходится» там, где проверять нечем |
| Несуществующий эксперимент — пустая страница | Нет 404 |
| Данные проверяются на каждый показ | Проверка пошла без запроса |
| Ссылка рейтинга теряет набор параметров | Число прогонов не совпало |
| Ячейка карты перестаёт быть ссылкой | Ссылок на прогоны не нашлось |
| Доля ненадёжных исчезает из рейтинга | Нет колонки |
| Предупреждение AN-3 убрано | Нет текста про фильтр по паре |
| Происхождение молчит о смене кода | Нет «код изменился» |
| Команда воспроизведения не печатается | Нет строки `run-experiment` |
| Ошибка упавшего прогона не показывается | Текст ошибки пропал |

### Что затронуто вне нового модуля

- `admin/web.py` — четыре маршрута и `Shell`: шапке страницы нужны имя
  эксперимента и время, а не всё состояние платформы (0,19 с ради строки
  заголовка).
- `admin/templates/base.html` — пункт «Эксперименты» в навигации и стили карты,
  происхождения и кривой; внешних адресов по-прежнему ноль.
- `tests/test_admin_state.py` — запрет своего доступа к данным распространён на
  весь пакет `admin` и сформулирован точнее: запрещены свои движки
  (`import duckdb`/`sqlite3`/`pyarrow`) и свои формулы путей, а не подстроки.
