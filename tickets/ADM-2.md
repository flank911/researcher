# ADM-2 — `status`: одна команда отвечает, живо ли всё

- **Эпик:** E10 — Админка
- **Статус:** done
- **Зависимости:** ADM-1
- **Критический путь:** нет (но даёт почти всю наглядность за наименьшую цену)

## Описание

Команда `trading-research status`: состояние данных, расписания, валидации и
экспериментов одним вызовом, без обращения к API и без записи.

## Контекст

README описывает проверку «живо ли расписание» как процедуру из трёх шагов, и
главный из них — **запустить сбор руками** и посмотреть, догружает он что-нибудь
или говорит «актуален, догружать нечего». Проверка состояния через изменение
состояния работает, но у неё два изъяна: она ходит в сеть и она отвечает только
про один из четырёх контуров. Про остальные три (качество данных, состав
результатов, незакрытые прогоны) такой процедуры нет вовсе.

Отставание свечей на трое суток ([ADM-1](ADM-1.md), находка 1) — пример того,
что эта команда показывала бы первой строкой.

Эта команда ценна и сама по себе, и как проверка [ADM-1](ADM-1.md): если
read-model собран правильно, `status` — это только форматирование.

## Решение

```
trading-research status [--config <path>] [--json] [--strict]
```

Четыре блока, по строке на сущность — формат как у `update-data` и
`validate-data` (что было, что есть, чего не хватает):

```
Данные
  BTCUSDT 1h candles: 2022-01-01 … 2026-10-31 07:00, 41 617 бар, отстаёт на 68 часов
  BTCUSDT 1h open_interest: … 2026-11-02 18:00, 703 точки, запас до потери 27 суток
Расписание
  сбор рыночных рядов: жив (по данным), последняя итерация 2026-11-02 18:40, exit=0
Валидация
  ma_cross_multi: проверено 2026-10-31 02:01 (3 суток назад), дефектов нет
Эксперименты
  ma_cross_multi: 684 прогона, все completed, ненадёжных по числу сделок 312 (46%)
```

Код возврата: `0` — вмешательство не требуется; `1` под `--strict` — требуется.
Поводы для `1`: отставание ряда больше чем на N периодов, запас OI/LS меньше 7
суток, дефекты в последней валидации, прогоны в статусе не `completed`,
отсутствие отчёта валидации вовсе.

Порог запаса — 7 суток, и это не круглое число ради круглости: окно биржи 30
дней, интервал сбора 6 часов, то есть неделя — это 28 пропущенных итераций
подряд. Раньше — ложная тревога, позже — поздно.

`--json` обязателен: он делает командой, а не экраном, то, что потом читает
веб-админка ([ADM-3](ADM-3.md)) и внешнее расписание. Иначе единственным
потребителем состояния окажется HTML.

## Критерии приёмки (DoD)

- [x] Команда не делает ни одного сетевого запроса и ничего не пишет в store.
- [x] На сегодняшнем store показывает отставание свечей (трое суток) и запас по
      OI/LS — замер приложен к тикету.
- [x] `--strict` даёт код 1 на каждом из поводов; на каждый повод есть тест.
- [x] Пустой store и отсутствие эксперимента не падают, а печатают «нет данных».
- [x] `--json` отдаёт те же числа, что текстовый вывод (тест на согласованность).
- [x] Раздел README «Как проверить, что расписание живо» переписан на эту
      команду: запуск сбора руками остаётся как способ **починить**, а не
      проверить.

### Что команда говорит на сегодняшнем store

```
Данные
  BTCUSDT 1h candles: 2022-01-01 00:00 … 2026-10-31 07:00, 42 344 бара, отстаёт на 84 периода
  BTCUSDT 1h open_interest: 2026-10-02 00:00 … 2026-11-03 12:00, 781 точка, отстаёт на 7 периодов, запас 28 суток 16 ч
Расписание
  последняя итерация 2026-11-03 13:54, 5 ч 51 мин назад, exit=0
Валидация
  отчётов 24 из 24, дефектов нет, без даты 24
Эксперименты
  684 прогона (completed: 684), ненадёжных по числу сделок 312 (46%), последний 2026-10-30 08:16
Внимание
  данные: BTCUSDT 1h candles — отстаёт на 84 периода (3 суток 12 ч)
  ...
  валидация: вердикт без даты у 24 отчётов: покрытие текущих данных не определить
итого: требуется вмешательство — 7 поводов (валидация, данные)
```

Семь поводов: шесть пар свечей отстают на трое суток и 24 вердикта валидации без
даты. `--strict` на этом состоянии даёт 1, без него — 0. Ни одного обращения к
API: команда отвечает про все четыре контура, не меняя ни одного из них.

### Порог для OI/LS пришлось пересмотреть после первого же прогона

Тикет говорил «отставание ряда больше чем на N периодов» одинаково для всех
рядов. На живом store это сразу дало **ложную тревогу**: open interest и
long/short ratio на 1h отставали на 7 периодов при живом сборе и `exit=0` — и
должны были, потому что их создаёт расписание раз в шесть часов. Порог в периодах
измерял не здоровье ряда, а частоту сбора.

Поэтому отставание осталось поводом только у рядов, которые можно догрузить в
любой момент (свечи, funding). У OI/LS поводов два, и оба про то, что с ними
действительно может случиться: запас до потери истории меньше недели и тишина в
логе сбора дольше суток. Смерть расписания видна обоими способами, а нормальная
работа больше не выглядит аварией.

### Пороги и почему они такие

| Порог | Значение | Почему |
|---|---|---|
| Отставание ряда | 3 периода | один период — текущий бар ещё не закрыт (OPS-2 его намеренно не берёт), два — запуск не совпал с границей, три подряд — ряд не наполняется |
| Ряд без периода (funding) | сутки | расписание выплат задаёт биржа; выплаты раз в 8 часов, значит сутки тишины — пропуск |
| Запас OI/LS | 7 суток | окно биржи 29 суток, сбор раз в 6 часов: неделя — это 28 пропущенных итераций подряд |
| Вердикт старше данных | не порог | точное сравнение `checked_at` с последней точкой ряда: проверка просто не видела того, что лежит в store |

Вердикт **без даты** — отдельный повод, и это осознанно: покрытие текущих данных
по нему не определить в принципе. На сегодняшнем store таких 24 из 24, и повод
снимается первым же прогоном `validate-data`, который теперь ставит время
([ADM-1](ADM-1.md)).

### Чего команда поводом не считает

| Не повод | Почему |
|---|---|
| Лога сбора нет | расписание может быть не поднято на этой машине — это решение владельца; вердикт о сборе всё равно дают данные |
| funding/OI/LS отсутствуют | они опциональны по контракту `build_features`; так же на них смотрит `validate-data` ([DATA-8](DATA-8.md)), а расхождение двух команд на одном вопросе было бы хуже любого из двух ответов |
| Эксперимента нет | «прогонов ещё не было» — состояние платформы, а не неисправность |
| Пустые свечи | **повод**: прогонять не на чем |

### Проверка тестов

Восемь мутаций — по одной на каждое решение о пороге:

| Мутация | Упало тестов (из 22) |
|---|---|
| порог отставания: `>=` вместо `>` | 1 |
| отставание OI/LS тоже повод | 1 |
| отсутствие funding/OI/LS тоже повод | 2 |
| вердикт без даты не считается поводом | 1 |
| вердикт старше данных: сравнение наоборот | 2 |
| запас ниже порога не считается поводом | 3 |
| `--strict` не влияет на код возврата | 1 |
| отсутствие лога — повод | 2 |

Ловятся все восемь.
