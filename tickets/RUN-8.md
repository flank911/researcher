# RUN-8 — Производительность walk-forward

- **Эпик:** E7 — First real research run
- **Статус:** todo
- **Зависимости:** RUN-7

## Описание

Две находки ревью в горячем пути walk-forward. Тикет **намеренно заблокирован на
RUN-7**: оптимизировать до замера на реальных данных — значит гадать, какая из двух
проблем вообще значима.

## Находки

**1. Отбор на train последовательный.**
[`_select_on_train`](../src/trading_research/experiments/walk_forward.py) прогоняет
полный бэктест по каждой комбинации параметров в простом цикле, хотя `parallel.py`
(EXP-5) готов. Итого `O(folds × combos)` последовательных прогонов. На сетке 9
комбинаций это незаметно, на 500 — определяюще.

**2. Линейные Python-сканы нарезки окон.**
`_slice_window` и `_window_segment` строят индексы через `enumerate` по всему
списку времён:

```python
in_window = [i for i, t in enumerate(data_times) if window.start <= t < window.end]
```

Время отсортировано, так что это бинарный поиск (`bisect`) или фильтр Polars.
Сам скан дешёвый, но он внутри цикла по комбинациям внутри цикла по фолдам, то есть
умножается на то же `folds × combos` из находки №1.

## Решение

- Параллелить отбор на train через `run_parallel` (после RUN-1 он уже будет
  подключён к CLI-прогону — переиспользовать тот же механизм).
- Заменить линейные сканы на `bisect` по отсортированному времени либо на
  Polars-фильтр; выбрать по замеру, а не по вкусу.
- Условие приёмки — измеренное ускорение на профиле из RUN-7, а не «стало лучше».

## Критерии приёмки (DoD)

- [ ] Есть бенчмарк на размерах из RUN-7 (до/после, зафиксированные числа).
- [ ] OOS-результат **побитово** тот же, что до оптимизации (регрессионный тест на
      эквивалентность — ускорение не имеет права менять цифры).
- [ ] Параллельный отбор детерминирован: результат не зависит от числа воркеров.
- [ ] Ускорение воспроизводится, а не является шумом одного запуска.
