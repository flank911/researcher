# REG-4 — Окно retention Binance для OI/LS: кламп, внятная ошибка, пометка покрытия

- **Эпик:** E6 — Market Regimes
- **Статус:** done
- **Зависимости:** REG-1, RUN-2
- **Критический путь:** нет

## Описание

Binance отдаёт open interest и long/short ratio **только за последние ~30 дней**.
Пайплайн об этом не знает, поэтому на любом историческом прогоне две из девяти фич
режима молча пусты, а команда загрузки падает сырой ошибкой API.

## Контекст

Вскрыто первым реальным прогоном ([RUN-7](RUN-7.md)), исследуемый диапазон
2022-01-01 … 2026-10-01.

**1. Команда падает целиком.**

```
$ trading-research fetch-market-data --symbol BTCUSDT --timeframe 1h \
    --start 2022-01-01 --end 2026-10-01
BinanceAPIError: Binance API error 400: {"msg":"parameter 'startTime' is invalid.","code":-1130}
```

`startTime` вне окна retention — это `-1130`, а не пустой ответ. Проверено: 25 дней
назад эндпоинт отвечает, 30 — уже нет. Порядок рядов в `expand_series` таков, что
funding (у которого история есть вся) успевает записаться, а OI и LS — нет, и
пользователь получает traceback вместо «эти два ряда доступны только за 30 дней».
`_validate_period` в `cli/fetch_market_data.py` уже проверяет *интервал* агрегации —
проверки *диапазона* рядом с ней нет.

**2. Пустые фичи неотличимы от отсутствия связи.**

`time_slice_features` на прогоне RUN-7: `oi_change_pct` и `ls_ratio_avg` — 114 NULL
из 114 строк. `build-features` отработал с кодом 0 и не сказал ни слова. Дальше
`analyze-regimes` печатает по этим фичам `NaN` в одном ряду с настоящими
корреляциями, то есть «данных нет» выглядит как «корреляции нет» — ровно тот класс
тихого расхождения, от которого страховал [RUN-5](RUN-5.md).

## Решение

- `fetch-market-data`: знать про окно retention для OI/LS. Диапазон за его пределами
  — либо кламп к доступному окну с предупреждением, либо явная ошибка, называющая
  окно и способ обойти (`--series funding` для истории). Выбрать кламп: при
  `--series all` на историческом диапазоне команда должна загрузить funding за всю
  историю и OI/LS за доступные 30 дней, а не падать.
- `build-features`: печатать покрытие по каждой фиче (сколько слайсов заполнено) —
  пустая фича не должна проходить незаметно.
- `analyze-regimes`: отличать «нет данных» от «нет корреляции» — отдельная пометка
  или строка покрытия под матрицей.
- Если OI/LS нужны на истории — это отдельный тикет про другой источник или про
  инкрементальный сбор по расписанию; здесь только честность про то, что есть.

## Критерии приёмки (DoD)

- [x] `fetch-market-data --series all` на историческом диапазоне не падает: funding
      за весь диапазон, OI/LS за доступное окно, в выводе сказано, что окно урезано.
- [x] Ошибка `-1130` не доходит до пользователя сырой: сообщение называет окно
      retention и что делать.
- [x] `build-features` сообщает покрытие фич; фича без данных видна в выводе.
- [x] `analyze-regimes` не выдаёт `NaN` от пустых данных без пометки.
- [x] Тест на кламп диапазона — на подставном транспорте, без сети.

## Как сделано

Три части, у которых один корень — 30-дневное окно биржи, но разные места отказа.

### 1. Кламп окна и внятная ошибка

`clamp_to_retention` урезает начало окна для OI/LS. Выбран кламп, а не ошибка:
при `--series all` на историческом диапазоне команда должна загрузить funding за
всю историю и OI/LS за доступное окно, а не падать на втором ряде из трёх.

Функция **публичная и одна на оба пути**: ту же границу считает регулярный сбор
[OPS-1](OPS-1.md), когда решает, какая часть истории уже невосполнима. Две копии
этой формулы разъехались бы молча — расхождение проявилось бы только на краю окна.
Константы `RETENTION` / `SAFE_RETENTION` переехали из `cli/update_market_data.py`
в `market_data_client.py`, к `PERIOD_MS`: это свойства эндпоинта, а не команды.

Сырой `-1130` превращается в `RetentionWindowError` с объяснением. Тип отдельный,
а не текст в общем `BinanceAPIError`: по строке `parameter 'startTime' is invalid`
невозможно догадаться, что речь про 30-дневное окно. Сообщение собирается в обход
родительского конструктора — тот режет тело до 200 символов и срезал бы как раз
объяснение, ради которого тип и заведён. Прочие 400-е и не-JSON тела в этот тип
не попадают: выдавать чужую ошибку за проблему окна — то же враньё, только наоборот.

**Кламп вскрыл случай, которого не было в тикете.** Если запрошенный диапазон
старше окна *целиком*, начало после клампа уезжает за конец: `expected` уходил в
минус, а запрос — в `ValueError: end must be after start`, по которому про окно
retention не догадаться. Добавлен статус `OUT_OF_WINDOW` — отдельный и от
«покрытие полное», и от «покрытие неполное»: у биржи этих данных нет и не будет,
это не дефект загрузки. Код возврата остаётся нулевым (иначе `--series all` на
истории «падал» бы в смысле DoD), но строка говорит прямо, что данных нет и чем
их вообще добыть.

### 2. Покрытие фич в `build-features`

Устойчивость к отсутствию рядов имела цену: команда отрабатывала с кодом 0 и
молчала, когда фича выходила пустой целиком. `feature_coverage` считает
заполненность каждой фичи, команда печатает её сразу после пути к таблице.

Пустая таблица даёт одну строку, а не десять «пустых фич»: это один отказ, и
выдавать его за десять — тот же сорт неправды, что и молчание.

### 3. «Нет данных» против «нет связи» в `analyze-regimes`

`pl.corr` отдаёт `null` и когда связи нет, и когда коррелировать нечего. Для
читателя это разные ответы — «проверили, связи нет» против «не проверяли».
`regime_feature_availability` считает заполненность, команда печатает пометку под
матрицей. Отличается и второй источник `null` — одна точка, на которой корреляция
не определена. Когда данных хватает, пометка говорит об этом прямо, иначе она
превратилась бы в шум, который перестают читать.

Пояснительные строки печатает команда, а не кладёт в результат: матрица уходит и
в экспорт, где они были бы мусором в CSV.

## Проверено на живых данных

**Главный сценарий тикета** — тот самый вызов, который падал сырым `-1130`:

```
$ trading-research fetch-market-data --symbol BTCUSDT --timeframe 1h \
    --start 2022-01-01 --end 2026-10-01 --series all
funding BTCUSDT 1h: 5202 rows, 2022-01-01 00:00 … 2026-09-30 16:00 (период задаёт биржа…)
open_interest BTCUSDT 1h: НЕТ ДАННЫХ — весь запрошенный диапазон (2022-01-01 … 2026-10-01)
  старше окна доступности в 29 дней. Биржа эту историю не отдаёт; накопить её
  может только регулярный сбор (update-market-data).
long_short_ratio BTCUSDT 1h: НЕТ ДАННЫХ — …
exit=0
```

**Диапазон, пересекающий границу окна** — кламп виден:

```
open_interest BTCUSDT 4h: 168 rows, 2026-10-02 00:00 … 2026-10-29 20:00, покрытие полное
  ОКНО УРЕЗАНО: просили с 2026-08-01 00:00, биржа отдаёт только 29 дней,
  поэтому начало сдвинуто на 2026-10-01 20:22.
```

**Покрытие фич** на таблице прогона RUN-7 — ровно тот симптом, который тогда
нашли только через два шага пайплайна:

```
покрытие фич (114 слайсов): пустых — 2: oi_change_pct, ls_ratio_avg
  oi_change_pct: 0/114 слайсов (0%)  ← ПУСТО
  ls_ratio_avg: 0/114 слайсов (0%)  ← ПУСТО
```

**Корреляции** — `NaN` больше не стоит в одном ряду с настоящими числами:

```
ДАННЫХ НЕТ по фичам: oi_change_pct, ls_ratio_avg — null у них означает
«нечего коррелировать», а не «связи нет»
заполнено: market_return_pct 684/684, volatility 684/684, …
```

### Регрессия, которую поймал живой прогон, а не тесты

Кламп нормализует `start` в UTC, а `end` приходит из Typer наивным. На funding —
единственном ряде, который не клампится, — загрузчик сравнивал наивный конец с
UTC-aware началом и падал `TypeError: can't compare offset-naive and offset-aware
datetimes`. Тесты этого не ловили, потому что везде передавали aware-время,
которого Typer не даёт. Обе границы теперь приводятся сразу, добавлен тест,
проверяющий именно наивный вход.
