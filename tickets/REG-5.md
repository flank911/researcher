# REG-5 — Пагинация `/futures/data/*` молча теряет начало диапазона

- **Эпик:** E6 — Market Regimes
- **Статус:** done
- **Зависимости:** REG-1
- **Критический путь:** да (тихая потеря данных)

## Описание

`BinanceMarketDataClient._paginate` предполагает, что эндпоинт отдаёт данные **от**
`startTime` вперёд. Эндпоинты `/futures/data/*` (OI, LS) отдают **хвост** запрошенного
окна — последние `limit` точек. Курсор после первого батча оказывается за `endTime`,
цикл выходит, и начало диапазона просто не загружается. Без ошибки.

## Контекст

Вскрыто на прогоне [RUN-7](RUN-7.md). Запрошено окно 28 дней (672 часовых точки),
`limit=500`:

```
$ trading-research fetch-market-data --symbol BTCUSDT --timeframe 1h \
    --start 2026-10-02 --end 2026-10-30 --series open_interest
wrote 500 rows of open_interest for BTCUSDT 1h -> data/raw
```

Записано 500 строк из 672, и это `2026-10-09 05:00 … 2026-10-30 00:00` — хвост.
Первые семь дней окна отсутствуют, команда отчиталась об успехе.

Прямая проверка эндпоинта подтверждает: с `startTime` 28 дней назад, `endTime` сейчас
и `limit=500` ответ начинается не с `startTime`, а с `endTime − 500 периодов`.

Механика в `_paginate`: `cursor = int(batch[-1][time_key]) + 1`, а `batch[-1]` — это
самая свежая точка окна, не 500-я от начала. Условие `if len(batch) < limit: break`
тоже не спасает — батч полный. Для `/fapi/v1/fundingRate` логика верна (он отдаёт от
`startTime`), поэтому дефект проявляется только на OI/LS.

## Решение

- Пагинировать `/futures/data/*` **назад**: курсор — `endTime`, на каждом шаге
  сдвигать его к `startTime` на `limit` периодов (или на минимальный таймстамп
  батча − 1), пока не дошли до `startTime`.
- Либо нарезать запрошенный диапазон на окна по `limit` периодов и запрашивать
  каждое отдельно — проще и не зависит от направления ответа.
- Инвариант, который должен ловиться: число полученных точек соответствует
  запрошенному окну, а минимальный таймстамп — не позже `startTime` + период.

## Критерии приёмки (DoD)

- [x] Окно шире `limit` загружается целиком; покрытие проверяется по краям, а не
      только по числу строк.
- [x] Тест на подставном транспорте, который отдаёт **хвост** окна, — фиксирует
      именно это поведение Binance, а не удобное для кода.
- [x] `fetch-market-data` не отчитывается об успехе, если покрытие неполное.
- [x] Регрессия на funding: пагинация вперёд по `/fapi/v1/fundingRate` не сломана.

## Как сделано

Выбран второй из предложенных вариантов — **нарезка диапазона на окна** по
`limit` периодов. Он не зависит от направления ответа: в окне ровно `limit` точек,
поэтому «хвост» окна и есть всё окно. Пагинация назад осталась неиспользованной —
она продолжала бы зависеть от того, с какого края эндпоинт отдаёт данные.

`_paginate` разделён по фактическому поведению эндпоинтов:

- `_paginate_forward` — курсор, только для `/fapi/v1/fundingRate` (отдаёт от
  `startTime` вперёд);
- `_paginate_windows` — нарезка окнами, для `/futures/data/*`.

Ширина окна считается из периода агрегации, поэтому длительности интервалов
собраны в `PERIOD_MS`. `SERIES_PERIODS` в CLI теперь берётся оттуда же
(`tuple(PERIOD_MS)`), а не дублируется списком: загрузчику и валидации нужен один
и тот же набор, и разъехаться они больше не могут.

Пустой ответ цикл **не** прерывает — дыра в середине диапазона не должна отменять
загрузку остальных окон. Прежний `break` на пустом батче был ещё одним способом
молча потерять хвост.

### Побочная находка: `endTime` уходил включительно

Тест на funding, написанный против поведения живого эндпоинта, упал не там, где
ожидалось: вернулось 101 значение вместо 100. Причина — в запрос уходил
`endTime = end`, а Binance трактует его **включительно**, хотя контракт всех трёх
методов и всего остального кода (`fetch-data`, `DuckDBStore.read_window`, конфиг
эксперимента) — полуинтервал `[start, end)`. Точка ровно на правой границе
попадала и в текущее окно, и в следующее.

На свечах этот класс расхождения уже выписан как [DATA-7](DATA-7.md) — там он на
стороне валидатора. Здесь он на стороне загрузчика и исправлен вместе с основным
дефектом: запрос уходит с `end - 1 ms`, граница названа в докстрингах модуля и
`_fetch_batch`. Видно по данным: OI на 4h за то же окно даёт теперь 168 точек, а
не 169.

### Проверено на живом API

Тот же профиль, на котором дефект был найден (окно 28 дней, `limit=500`):

| Запрос | До | После |
|--------|-----|-------|
| OI BTCUSDT 1h | 500 строк, с 2026-10-09 05:00 | **672** строки, с 2026-10-02 00:00 |
| LS BTCUSDT 1h | 500 строк, с 2026-10-09 05:00 | **672** строки, с 2026-10-02 00:00 |
| OI ETHUSDT 4h | 169 строк (включая границу) | **168** строк, `[start, end)` |
| funding BTCUSDT, 2022-01-01…2026-10-01 | 5 202 строки | 5 202 строки — регрессии нет |

`validate_series` по загруженным рядам: `is_clean=True`, 0 дублей, 0 пропусков,
монотонность — то есть стык окон чист (672 точки при `limit=500` — это два окна,
стык есть).

### Вывод вместо «wrote N rows»

`fetch_market_data` возвращает `SeriesCoverage` (строки, края, ожидаемое число
точек), а не одно число: по числу строк полную загрузку от потерянной недели не
отличить — ровно на этом дефект и прожил весь прогон RUN-7. Статус покрытия
трёхзначный, потому что у funding период задаёт биржа и ожидание для него не
посчитать: `complete` / `incomplete` / `unverified` — последнее честнее, чем
отвечать «полное» там, где проверки нет.

Неполное покрытие даёт код возврата 1 и строку, называющую нехватку и потерянный
край; записано при этом то, что получено, и в выводе это сказано. Клампа диапазона
под окно retention здесь нет — это [REG-4](REG-4.md); после него урезанное окно
будет покрыто полностью и код вернётся к нулю.
