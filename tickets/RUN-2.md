# RUN-2 — CLI загрузки рынок-данных (funding / OI / LS ratio)

- **Эпик:** E7 — First real research run
- **Статус:** done
- **Зависимости:** REG-1, EXP-6

## Описание

Команда `fetch-market-data` поверх `BinanceMarketDataClient` (REG-1) и
`ParquetStore.write_series` (DATA-2). Без неё funding/OI/LS невозможно загрузить
иначе как из Python, и весь эпик E6 на реальном прогоне остаётся без данных.

## Контекст

`fetch-data` ([cli/fetch_data.py](../src/trading_research/cli/fetch_data.py))
загружает **только OHLCV** — она жёстко завязана на `KlineFetcher`/`fetch_klines` и
`write_candles`. При этом REG-1 уже реализовал три метода загрузки
(`fetch_funding_rate`, `fetch_open_interest`, `fetch_long_short_ratio`), а DATA-2 —
парную запись/чтение рядов (`write_series` / `read_series`). Связки между ними нет.

Следствие: BT-6 (funding в PnL) на реальном прогоне тоже остаётся без входных
данных — движок принимает `funding=None` и молча считает PnL без funding-платежей.

## Решение

Команда с выбором ряда и переиспользованием диапазона/путей из `fetch-data`:

```
trading-research fetch-market-data --symbol BTCUSDT --series funding \
  --start 2021-01-01 --end 2026-10-01 [--data-root data/raw]
```

- `--series funding|open_interest|long_short_ratio|all`;
- идемпотентная запись через `write_series` (upsert, как у свечей);
- бизнес-логика в `cli/fetch_market_data.py` — тестируется без сети через
  подставной клиент, как сделано для `KlineFetcher`.

## Критерии приёмки (DoD)

- [x] Три ряда загружаются и читаются обратно через `read_series`.
- [x] `--series all` загружает все три за один вызов.
- [x] Повторный запуск идемпотентен (upsert, без дублей).
- [x] Тесты без сети (подставной клиент), как в `test_cli.py`.
- [x] Интервалы OI/LS, не поддерживаемые Binance, дают понятную ошибку, а не
      пустой результат.

## Как сделано

`cli/fetch_market_data.py` + команда `fetch-market-data`. Бизнес-логика отделена от
Typer-обёртки и тестируется через `MarketDataFetcher`-протокол, как `KlineFetcher` в
EXP-6 — сети в тестах нет.

**Один интервал, две роли.** `--timeframe` служит и ключом партиции, и значением
`period` для Binance-эндпоинтов OI/LS. Layout повторяет свечи
(`{data_root}/{dataset}/exchange=…/symbol=…/timeframe=…/year=…/month=…`), поэтому
RUN-3 сможет читать ряды теми же ключами, какими читает свечи.

**Почему валидация интервала — отдельный пункт DoD.** `/futures/data/*` принимает
только фиксированный набор `period` (`SERIES_PERIODS`: 5m…1d). На неподдерживаемом
интервале Binance отвечает пустым списком, то есть «успешной» загрузкой нуля строк —
это выглядит как отсутствие данных за период, а не как неверный запрос. Поэтому
проверка идёт до обращения к сети и падает с перечислением допустимых значений.

У funding своего интервала нет (расписание выплат задаёт биржа), поэтому ограничение
на него не распространяется — зафиксировано тестом, чтобы ограничение не «переехало»
на funding при будущих правках.

Побочно: это закрывает тихий пробел BT-6. Движок умеет учитывать funding в PnL, но
получал `funding=None`, потому что данные нечем было положить на диск, — и считал
PnL без funding-платежей без единого предупреждения.

Непокрытой осталась одна защитная ветка (`_fetch_one` при `SeriesKind.ALL`): через
публичный API она недостижима, так как `expand_series` никогда не возвращает `ALL`.
Оставлена как страховка на случай добавления новых значений в enum.
