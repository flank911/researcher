# OPS-2 — Догрузка свечей и funding от последнего бара

- **Эпик:** E8 — Эксплуатация данных
- **Статус:** todo
- **Зависимости:** DATA-2, EXP-6
- **Критический путь:** нет

## Описание

`fetch-data` и `fetch-market-data` всегда запрашивают у API весь указанный
диапазон, даже если он уже в store. Расширить покрытие базы (новый месяц, новый
символ, новый таймфрейм) можно только вручную — подобрав окно так, чтобы не
перекачивать годы.

## Контекст

Запись идемпотентна: `ParquetStore._upsert` склеивает партицию и снимает дубли по
времени, так что повторный прогон данные не портит. Платит он за это сетью и
временем: наполнение текущего состояния (156 060 свечей, 6 пар) заняло 87 с — и
столько же займёт любое повторное «добить до сегодня», потому что диапазон
запрашивается целиком.

Это не ошибка, а отсутствие удобства, из-за которого регулярное наполнение базы
делается руками. [OPS-1](OPS-1.md) решает ту же задачу для OI/LS, где она
критична; здесь — то же для рядов, которые догружаются в любой момент.

## Решение

- Флаг вида `--since-last` (или отдельная команда `update-data`): прочитать
  последний таймстамп по паре из store, запросить только `[последний + период, end)`.
- Пустой store — не особый случай: падать на отсутствии данных команда не должна,
  границу берёт из конфига.
- Работать по конфигу эксперимента (символы, таймфреймы, диапазон) — как
  `build-features`, чтобы одна команда закрывала весь набор пар.
- Явно печатать, что было в store и что дописано: «BTCUSDT 1h: было до
  2026-09-30 23:00, дописано 720 бар до 2026-10-30 23:00».

## Критерии приёмки (DoD)

- [ ] Догрузка запрашивает только недостающий хвост; объём запроса видно в выводе.
- [ ] Повторный запуск без новых данных не обращается к API зря и ничего не меняет.
- [ ] Пустой store обрабатывается как полная загрузка из конфига.
- [ ] Новый символ или таймфрейм в конфиге загружается с нуля той же командой.
- [ ] Тест на подставном транспорте: догрузка хвоста, пустой store, повторный
      запуск без изменений.
